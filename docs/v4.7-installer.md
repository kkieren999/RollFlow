# V4.7 Windows installation — unsigned staging

Two Inno Setup 6 wizards: LocalLab full portable runtime with protected database and separate fictional training, Workstation lightweight embedded Python and HTTPS browser launcher, no server or local DB. Per-user version-specific installation, Start menu shortcuts and optional desktop shortcuts, no elevation, no automatic start/init/upgrade. LocalLab runtime deliberately has no automatic uninstaller because existing PostgreSQL instances may reference it. Retain old runtime directories until ICT verifies all state configurations and backups. Workstation uninstall removes application files only, preserving server preference; users/ICT can remove preference separately. New version installs side-by-side. Same-version overwrite refused. No credentials or data packaged.

Workstation: configure exact ICT-approved HTTPS DNS hostname (default TLS port, no URL credentials/path/query, no HTTP); explicit confirmation, local URL-only preference, default browser sign-in, TLS verification by browser; optional diagnostic uses system trust, no redirects or TLS bypass. Staff must never connect to unknown servers or open local database for operational data. The central service remains existing loopback Django/Waitress and PostgreSQL with school-mode TLS proxy settings. ICT must configure approved proxy/DNS/firewall/service account and Windows service supervision separately; do not expose PostgreSQL or Waitress directly. No service auto-registration or live deployment.

Full local package includes SHA256 manifest; verifier detects file corruption, does not establish publisher authenticity. Setup binaries checksums published in CI. No code-signing certificate provided; these installers remain unsigned STAGING. For production signing use school-approved Authenticode signing and timestamping process on controlled build machine, verify signer and hash before distribution. Never commit signing private keys, passwords, PFX or real data. Controlled update = download verified approved version, install side-by-side, stop prior runtime, private snapshot and explicit upgrade, review migrations, start new version. No auto-update or automatic downgrade.

Native snapshot: stopped instance only; archive and key plus PostgreSQL dump, private filesystem ACL, hash manifest and pg_restore listing. Contains private data, must be stored on approved encrypted storage. Upgrade creates sealed snapshot before migrating; failure after migration starts sets recovery-required.lock so new launcher refuses start/manage. Do not delete guard or run old code against migrated database. Restore-staging requires a verified staging snapshot, independent unused state directory and distinct ports; creates new database, restores dump/archive, migrates, clears sessions and validates; original remains untouched. Example: python/python.exe -m deployment.native --state <new-state> restore-staging <snapshot-folder> --db-port 55439 --web-port 18089. Production recovery, offsite encrypted storage, retention, RPO/RTO and independently approved drill remain outstanding. Diagnostics omit credentials and logs.

CI builds both setup files, installs in isolated test paths, verifies manifests and checks workstation contains no server. Existing portable/native migration tests retained. Final CI status must be checked. Full protected multi-user browser, ICT/SSO/MFA, approved OneSchool transfer, independent security/load and recovery approval are required before real use.

V4.7 adds an installed-application protected Chrome smoke on the disposable restored staging database: three independent accounts, real sign-in, roster isolation, certified submission, monitor summary without student names and denied direct URL access. Linux native smoke also restores a sealed snapshot into new ports/state. These are narrow regression gates, not full workflow/load/concurrency acceptance. Installer compilation and all smoke results require CI confirmation.
