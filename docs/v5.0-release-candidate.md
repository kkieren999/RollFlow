# RollFlow V5.0 RC1 — production launch preparation

**Not a production release.** All prior modules remain cumulative. Version 5.0.0-rc.1, unsigned synthetic staging. School mode initialization, native operations and actual WSGI startup are blocked by code-level release policy (school and live timetable flags); environment variables and local checklist files cannot waive it. Staging remains usable. Management/settings checks on synthetic infrastructure do not authorise serving real school records. A later independently reviewed code release must close the open gates; never edit the policy simply to get a green result. No signing credentials, real records, integration secrets, deployment or release publication.

## ICT release checklist (open; evidence to be maintained privately)

| Gate | Required objective evidence | Accountable approval |
|---|---|---|
| Identity | Approved IdP registration, immutable account binding, MFA enforced by provider, revocation/disabled-user and session tests; no fallback local production login | ICT identity owner |
| OneSchool | Authorised exchange process, reviewed formats, complete enrolment history, reconciliation and rollback, correction and delivery confirmation | School data owner |
| Security | Independent code and infrastructure review, threat model, resolved vulnerabilities, dependency inventory, access and negative tests | ICT security |
| Privacy | Approved data classification, access/retention/deletion and export policies, support confidentiality, disclosure controls | School privacy/records owner |
| Operational | School sign-off on historical attendance, movement handover, delegation, relief, classroom and support gaps | Operational leaders |
| Deployment | Signed build hash, Authenticode trust and timestamp, approved central hostname/TLS/proxy, managed workstation config, restricted service identity, no direct DB access | ICT deployment |
| Recovery | Encrypted offsite backups incl. key, validated restore in isolated environment, retention, documented recovery targets and migration rollback | ICT operations |
| Capacity | Actual school-sized synthetic load, simultaneous use, accessibility, outage and recovery tests | ICT + pilot lead |
| Pilot | Training, support, incident process and signed go-live decision for the exact reviewed version | Principal/authorised governance |

No approvals are inferred. Do not store approval documents with private data in this public repository. Current fixed gate list is in rollflow/release_policy.py. Run deployment.release_readiness --json (or --bundle <installed-dir>) to inspect locally; --require-production returns 2 while blocked. Hash verification does not establish publisher trust. Native operations use an exclusive cooperative state lock; older binaries and direct processes do not obey it, so stop/retire old code under ICT control. Interrupted operations require manual investigation; never delete locks to bypass an active operation. Recovery additionally validates dump magic and allowed archive entries before creating fresh state.

## Rollout plan (fictional only until approval)

1. Use tested unsigned RC only on isolated approved test equipment. Download from exact successful CI artifact, check manifest, record commit and hashes. Never use real names, IDs or departmental credentials.
2. Local lab: install version alongside prior runtime; verify manifest, initialize a fresh synthetic database or restore verified synthetic snapshot, create individual fictional users. Test all protected workflows with distinct accounts, no shared admin logins.
3. Validate central architecture in ICT-approved isolated environment using synthetic data; no live school mode in this candidate. Workstation installer is an HTTPS browser launcher, not a managed endpoint configuration. No direct exposure of Waitress or PostgreSQL, no self-signed certificate bypass, no automatic updates.
4. Before real pilot, close every gate above and outstanding detailed phase acceptance items in docs and permanent handover. Require independent sign-off on exact release and deployment. Set policy for role scopes and timeouts, approved data transfer, manual fallback.
5. When authorised by school, pilot small staff cohort using approved signed release; review metrics and failures daily. Scale only after acceptance. If an outage or integrity issue occurs, stop new writes and follow approved school attendance/incident procedure, preserve audit and backups. Never run old code on migrated database; restore to new approved environment and reconcile outstanding records before resuming.
6. Establish responsible ICT service owner, support contact, training facilitator, incident escalation, release review and recovery drill schedule. No external notifications or automatic production deployment in this RC.
