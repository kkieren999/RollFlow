# RC3 administrator and recovery handbook — fictional staging

## Daily review
Open Administration Portal → System Settings & Readiness → Pilot Readiness. Check source provenance, publication coverage, pending verification, effective grants and audit separately. A recorded grant is not necessarily effective. Recheck access after staff changes; do not reuse shared accounts, disclose reset credentials or assume administrative access grants report exports. Account deactivation and explicit grant revocation use existing guarded workflows.

Review outstanding attendance, overdue movements, relief and workforce conflicts through authorised modules. Do not treat empty records as confirmed attendance or location. Retain original revisions when making reviewed corrections; local OneSchool reconciliation is not external delivery confirmation. Do not add actual records.

## Snapshot and isolated restore (P10)
1. Stop the web process and database using the normal launcher; ensure no other instance or direct process writes to that state. Record exact build and state path privately.
2. Choose a new snapshot folder on approved encrypted storage outside PostgreSQL storage, with restricted ACLs. In PowerShell from the Local Lab folder use `.\python\python.exe -m deployment.native --state "C:\approved-lab\RC3-test" snapshot "E:\approved-encrypted\RC3-snapshot"`. Example paths only; replace with authorised locations. Do not copy a running database directory.
3. Confirm snapshot succeeds and manifest is verified. Snapshot includes database dump and encrypted import archive/key if present; the dump itself is not encrypted by RollFlow. Protect the entire snapshot and key. Never upload snapshot, logs, credentials or identifiers to public GitHub.
4. On approved isolated equipment, restore only into a new state with unused distinct ports: `.\python\python.exe -m deployment.native --state "C:\approved-lab\RC3-restore" restore-staging "E:\approved-encrypted\RC3-snapshot" --db-port 55440 --web-port 18089`. Ensure bundled PostgreSQL is present; use explicit approved runtime path if needed. Verify hashes and exact release first.
5. Verify synthetic student/roll counts, original and corrected revisions, movement history, private notices, import archive and access policy; old sessions should be invalidated. Confirm source state is untouched. Measure elapsed recovery and compare to privately agreed recovery objectives. Test failure and rollback with disposable fixtures only.
6. If restore/upgrade leaves recovery-required.lock or another operation marker, preserve state; contact ICT, do not remove a marker or start old code against migrated data. Restore again into a different new directory after investigation.

## Outage and escalation (P11)
For unexpected permissions, mismatched identities, suspected disclosure, unreconciled writes or failed integrity checks, stop new writes and notify the nominated ICT/security and operations contacts through approved channels. Use existing approved school attendance/incident procedures; preserve relevant logs privately with access restrictions. Do not email data or share logs publicly. ICT coordinates diagnosis, recovery and reconciliation before resuming. Do not claim external notification or delivery through RollFlow. Record event, impact, authorised decision and follow-up privately.

## Proposed ownership
ICT owns deployment, security, recovery and monitoring; school data owner owns source correctness; operational leaders own workflow acceptance; authorised governance owns final go/no-go. Complete names, contacts, backup retention, escalation response and recovery objectives in approved private systems, not this repository.
