## Implementation workstreams, in order (one cumulative UI parity branch)
0. Reference capture and test specification. Pin exact website SHA, run website fixture with local HTTP server serving real CSS, capture rendered navigation/tabs and every role page/state, including dialogs, at 1440x900, 1366x768, 1024x768, 820x1180 and 390x844; dark/light, keyboard, empty/loading/error/expired, date changes. Existing tests also check 1100/600 widths and weekly geometry. Run equivalent protected installed server with deterministic synthetic database and matched explicit grants. Inventory route, action, scope, data source, state, test, screenshot pair, status (visual-only/partial/missing/approved exception); use real Playwright DOM snapshots/screenshots and user review, not just markup or hard-coded menu counts.
1. Single application shell and design system. New shared protected base and CSS components from website design-system, compact grouped side navigation, active states, tabs, header/date/user menu, notice bell, light/dark preference, icons, accessible dialog/form/table/status/card tokens. Preserve labels/order/layout from reference where authorised; replace disconnected live_base, ui_header, school_access_head, staff_portal/legacy templates progressively. Make login visually consistent but retain real credentials, session/CSRF, logout POST, staging label and no public demo credentials in protected app. No localStorage for school records or access authority. Server constructs menu and tab projections from eligible_account, can_teach, explicit active scoped grants, and true admin authority. Hidden controls not security; direct routes still checked. Account/role grant form context-sensitive scope/capabilities, clear disabled/explanation, template copy and expiry retained; no widened grants.
2. Teacher experience first. Reference Daily Schedule day/week, Brisbane date selection, Care/period cards with timings/room/status/spares/duties/closure/relief, consistent week grid; Master Timetable read-only scope approved, Class Finder filters/detail, Student Search scoped identity/detail, class list and seating UI, attendance P/A/L per student, draft/submit/lock and stale conflict, classroom action wizard, student support tabs and follow-ups. Existing /live/day/, /teacher/week/, /live/roll/, /live/classroom/ and teacher/master (currently redirects teachers to own timetable when connected), published directory /workspace/ routes are foundations. Missing read-only date projections, own attendance analytics and historical enrolment, teacher master/finder/student scope need new reviewed backend work; not merely copy website's school-wide demo access. Keep attendance certification, actual date, roster token, frozen revisions, transaction and no historical writes by UI workaround. Seating geometry/keyboard accessible controls over validated plans, no relief editing of regular teacher plans.
3. Student workflows. Website movement issue wizard, search, destinations, stats and log with View in day; student-day Care + periods 1–4, multiple visits and out-of-period departures. Existing /live/movements/, issue/detail/change and destination grants; use actual published date/period/time not hard-coded demo periods, open cross-day cases visible, preserve receiver/issuer state and closure reason; new safe per-student history projection, no sensitive clinical narrative. Classroom action and support wizard, observation/task/referral/follow-up tabs; current named tasks/referrals only; missing follow-ups/incident workflow and delegated scoped requests need structured categories, recipient checks, lifecycle, audit and data minimisation. No arbitrary wellbeing/discipline fields or demo text stores.
4. Leadership and operations. School principal/deputy, faculty HOD, year YLC/HOY, business/office dashboards with contextual tabs, scope-specific metrics, directory and timetable, attendance review, relief/availability, room changes, duty allocations and exceptions integrated into schedule (not redundant calendar/supervision menu). Match reference interaction where actually permitted. Existing /live/attendance/, /live/reports/, /live/workforce/, /live/workforce/mine/, /manage/attendance/relief/ provide safe backend. Current school-only monitoring, admin-only writes, 7-day current-publication report, support aggregates school-only, no broad faculty student access or year movement board, historical cover not proof; add explicit reviewed scoped capabilities and data projections for missing role functions, not grant broad admin. Partial-day and recurring duties, request/approval, notice expiry, historical reports/attendance and valid denominators are engineering gaps. Preserve small-cell suppression, report/export separate, audit and source readiness.
5. Administration parity. Website Dashboard, Staff Management, Student Management + Student Actions tabs, Timetable Management + master/classes, Attendance Overview, Student Movements, Account Management + roles, Audit & Activity, OneSchool Import Centre + Data, Settings. Existing /manage/, /manage/staff/, /manage/students/, /manage/classes/, /manage/timetable/, /manage/master/, /manage/oneschool/documents/, /manage/connected/dated/, /manage/access/, /manage/security/templates/, /manage/security/history/, /manage/school-data/ etc. Connect real forms and reviewed imports, previews, validation, versions, mapping and manual transfer; no dummy actions/placeholder counts. Distinguish admin-only tools from delegated staff and teaching. No real OneSchool data or credentials.
6. All-role acceptance and packaging. Seed reproducible fictional protected database with representative school days, students, classes, scoped grants, multiple teachers, relief and staff workflows; no auto-seeding over existing state. Build same protected UI in normal browser and Windows setup. Side-by-side screenshot pairs/DOM route and state assertions, positive/negative tests of every permitted control and direct URL, data persistence across browser sessions, cross-scope, expiry, concurrent operations, mobile/desktop layouts, contrast, keyboard, no external network dependency. Every referenced workflow has mapped backend test and browser test or explicit approved exception; don't claim 100% because counts match. CI compare actual installed protected server, not training-to-training. Keep training separately fictional, preserve website main, RC1 artifact evidence, migrations/backups, school startup hold; draft PR and verified versioned artifacts. Supply visual preview evidence and portable/installer download only after exact build passes. A hosted private synthetic preview is optional separate approval/config; no hosting/deployment promised.

## Acceptance rule
A normal user signs in to http://localhost:18087/ (protected workspace), sees the reference design and role-appropriate navigation and can carry out each approved workflow using central persistence. No need to switch to the fictional training demo to access intended functionality. No fake or inaccessible controls, no silent broadening of permissions. Verify every role with screenshot pair and tested interactions; user review at each milestone. No approval or real records until V5.0 production hold cleared in independently reviewed later release.
